### MythicEnchants Support Example

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Enchant-Plugins

An example implementation of the `EnchantPlugin` interface for the MythicEnchants plugin. It demonstrates how to check if an enchantment is a `MythicEnchant`, how to generate a `NamespacedKey` specific to the plugin, and how to add enchantments to an item's lore using `ItemStackBuilder` and `LoreBuilder`.

```java
public class MythicEnchantsSupport implements EnchantPlugin<MythicEnchant> {
    @Override
    public boolean isCustomEnchant(Enchantment enchant) {
        return enchant instanceof MythicEnchant;
    }
    @Override
    public NamespacedKey getNamespacedKey(String key) {
        return new NamespacedKey(MythicEnchants.inst(), key);
    }
    public void handleEnchant(ItemStackBuilder builder, MythicEnchant enchant, int level) {
        Validate.isTrue(level > 0, "Level must be strictly positive");
        // Type cannot be changed. Must make sure that item is an enchanted book
        if (!builder.getMeta().hasItemFlag(ItemFlag.HIDE_ENCHANTS))
            builder.getLore().insert(0, LoreParser.formatEnchantment(enchant, level));
    }
}
```

### MMOItems Upgrade Recipe Configuration

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Upgrading-Recipes/diff

Details the configuration syntax for upgrade recipes in MMOItems, contrasting it with standard crafting recipes. It specifies the use of 'item' instead of 'output' and outlines player requirements for using such recipes.

```APIDOC
Recipe Configuration Syntax:

Upgrade recipes differ from crafting recipes by using the 'item' key instead of 'output' in the first line of the recipe configuration.

Example:
item: "STEEL_SWORD"

Player Requirements for Upgrade Recipes:
- Must meet a minimum player level (e.g., level 5).
- Must possess specific items in their inventory (e.g., 4 steel ingots).
- Must have the item they are trying to upgrade in their inventory (this is an implicit ingredient).

Limitations:
- Upgrade recipes do NOT support crafting time; they are always instant.
- Failure to meet requirements results in an error message for the player.
```

### MMOItems Recipe Input Syntax

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Custom-Recipes/diff

Defines the format for specifying ingredients in custom recipes. It distinguishes between custom MMOItems and vanilla Minecraft items, including quantity ranges.

```APIDOC
Recipe Input Syntax:

- `m<MMOITEM_TYPE> <MMOITEM_ID> <quantity_range>`: Specifies a custom MMOItem as an ingredient.
  - Example: `mEXAMPLE_MMOITEM_TYPE EXAMPLE_MMOITEM_ID 1.0..`
- `v<VANILLA_ITEM_ID> <quantity_range>`: Specifies a vanilla Minecraft item as an ingredient.
  - Example: `vSTONE - 1.0..`

- `quantity_range`: Defines the amount of the item required. Can be a fixed number, a range (e.g., `1.0..2.0`), or open-ended (e.g., `1.0..`).
- Slotting: The position of the input in the recipe definition corresponds to the crafting grid slot. Left inputs map to left slots, right inputs to right slots.
```

### MMOItems Recipe Trigger Types

      - name: type
        type: string
        description: The ID of the vanilla item.
      - name: amount
        type: integer
        description: The quantity of the item to give.

    description: Gives an MMOItem to the player.
    format: "mmoitem{type=SWORD;id=FALCON_BLADE;amount=1}"

        type: string

        type: string
        description: The unique ID of the MMOItem.
      - name: amount
        type: integer
        description: The quantity of the MMOItem to give.

    description: Casts a MythicMobs skill.
    format: "mmskill{id=MythicMobsSkillInternalName}"
    parameters:
      - name: id
        type: string
        description: The internal name of the MythicMobs skill to cast.

  - name: experience
    description: Gives the player MMOCore experience.
    format: "exp{profession=<PROFESSION>;amount=<AMOUNT>}"
    parameters:
      - name: profession

### MMOItems API - NBTItem Usage

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Main%20API%20Features

Provides an overview of the NBTItem class for interacting with MMOItems NBT data. It covers methods for retrieving NBT data, checking for specific tags, and accessing tag values, noting differences for Minecraft versions.

```APIDOC
NBTItem:
  __init__(ItemStack itemStack)
    - Initializes an NBTItem from a Bukkit/Spigot ItemStack.
    - For Minecraft versions < 1.14, this uses NMS (Net Minecraft Server) code.
    - For Minecraft versions >= 1.14, it leverages the ItemMeta API.

  get(ItemStack itemStack): NBTItem
    - Static method to retrieve an NBTItem instance for a given ItemStack.

  hasType(): boolean
    - Checks if the NBTItem contains the MMOITEMS tag indicating it's an MMOItem.
    - Returns true if the tag is present, false otherwise.

  getType(): string
    - Retrieves the item type string (e.g., "SWORD", "AXE", "DAGGER") from the NBT data.
    - This method performs a map lookup and is recommended to be cached if called frequently.
    - Returns null or throws an error if the type tag is not found or invalid.

  getString(String key): string
    - Retrieves the string value associated with the specified NBT tag key.
    - Example: nbtItem.getString("MMOITEMS_ITEM_ID")

  hasTag(String key): boolean
    - Checks if a specific NBT tag exists within the NBTItem.

Dependencies:
  - Bukkit/Spigot API
  - NMS (for older Minecraft versions)

Limitations:
  - NBT handling can vary slightly between Minecraft versions.
```

### Available Recipe Trigger Types

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Recipe-Triggers/diff

Details the different types of triggers that can be used in recipes, along with their specific syntax and parameters. These triggers define actions performed when a recipe is crafted or otherwise processed.

```APIDOC
command:
  Description: Makes the console perform a command.
  Syntax: `command{format="<command_string>",sender=<SENDER_TYPE>}`
  Parameters:
    - format: The command string to execute. Can include placeholders.
    - sender: Specifies who executes the command. Available senders: PLAYER, CONSOLE, OP.
  Example: `command{format="give dirt",sender=OP}`

sound:
  Description: Broadcasts a sound to the player.
  Syntax: `sound{sound=<SOUND_NAME>;volume=<VOLUME>;pitch=<PITCH>}`
  Parameters:
    - sound: The name of the sound to play.
    - volume: The volume of the sound (e.g., 1.0).
    - pitch: The pitch of the sound (e.g., 1.0).
  Example: `sound{sound=entity.player.levelup;volume=1.0;pitch=1.0}`

vanilla:
  Description: Gives a vanilla Minecraft item to the player.
  Syntax: `vanilla{type=<ITEM_TYPE>;amount=<QUANTITY>}`
  Parameters:
    - type: The type of the vanilla item (e.g., DIAMOND, IRON_INGOT).
    - amount: The quantity of the item to give.
  Example: `vanilla{type=DIAMOND;amount=3}`

mmoitem:
  Description: Gives an MMOItems item to the player.
  Syntax: `mmoitem{type=<MMOITEM_TYPE>;id=<ITEM_ID>;amount=<QUANTITY>}`
  Parameters:
    - type: The type of the MMOItem (e.g., SWORD, ARMOR).
    - id: The unique ID of the MMOItem (e.g., FALCON_BLADE).
    - amount: The quantity of the item to give (optional, defaults to 1).
  Example 1: `mmoitem{type=SWORD;id=FALCON_BLADE} 2`
  Example 2: `mmoitem{type=SWORD;id=FALCON_BLADE;amount=1}`
```

### Prefix/Suffix Priority System

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Item-Modifiers/diff

Explains how MMOItems handles multiple prefixes or suffixes on an item. It prioritizes modifiers based on a defined priority value, keeping only the highest priority one. If no priority is set, a default system is used.

```text
When a modifier is selected during item generation, its suffix/prefix is automatically applied to the item. If multiple prefixes/suffixes are added, MMOItems only keeps the prefixes/suffixes with the highest priority, e.g an item which has `Sharp` with prefix priority 0 (0 is default priority) and `Fiery` with prefix priority 1 will only display `Fiery`. If you don't want to use the prefix/suffix priority system, just define the prefix/suffix using this format:
modifier:
  prefix: "YourPrefix"
  suffix: "YourSuffix"
```

### MMOItems Recipe Conditions

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Recipe%20Conditions

Details the various types of conditions that can be applied to crafting recipes in MMOItems. Each condition has specific parameters to define the requirement, and some allow for custom display text in the item lore.

```APIDOC
MMOItems Recipe Conditions:

General:
  Conditions are stored in a list within the recipe config section. Unlike ingredients, conditions do not take anything from the player inventory when using a crafting recipe.

Condition Types:

- level
  Usage: `level{level=<min>,consume=<true/false>}`
  Description: Players must be Lvl X or higher. `consume` is whether or not the levels should be consumed.

- class
  Usage: `class{list=<Class Name>,<Class Name 2>...}`
  Description: Restricts a recipe to certain classes.

- permission
  Usage: `permission{list="<perm1>,<perm2>";display="...";hide=false}`
  Description: Only players with specific permissions may use the recipe. `display` is how the condition looks like in the item lore. `hide` controls visibility when locked.

- placeholder
  Usage: `placeholder{placeholder="<Placeholder>~<Comparator>~<Number>";display="...";hide=false}`
  Description: Check the placeholder of a Player, then compare it to a number of your choice. Comparator list: `<`, `<=`, `>`, `>=`, `==`, `!=`. Use `eq` or `neq` when comparing strings. `display` customizes lore appearance, `hide` controls visibility when locked.

- food
  Usage: `food{amount=<amount>}`
  Description: The recipes consumes (and requires) X food.

- mana
  Usage: `mana{amount=<amount>,format="0.#"}`
  Description: The recipe consumes (and requires) X mana.

- stamina
  Usage: `stamina{amount=<amount>,format="0.#"}`
  Description: The recipe consumes (and requires) X stamina.

- money
  Usage: `money{amount=<amount>,format="0.#"}`
  Description: The recipe costs (and requires) X Vault currency.

- profession
  Usage: `profession{profession=<profession>,level=<min>}`
  Description: Players must be Lvl X in a profession or higher (MMOCore).

Recipe Options:

- hide-when-locked: This option triggers when at least one of the conditions is/are not met. The recipe will still display in the GUI if the player does not have all the required ingredients. Recipe conditions display at the beginning of the GUI recipe item lore.
```

### MMOItems Ability Modifier Configuration

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Complex-Stats/diff

Defines the structure for configuring ability modifiers within MMOItems. This includes setting base values, scaling factors, and maximum spread for properties like cooldown and duration. The format mirrors that of adding abilities to standard items, with specific handling for scalable values.

```APIDOC
Ability Modifier Structure:

  base: <value>
    - The base value for the ability modifier.

  scale: <value>
    - The scaling factor applied to the modifier based on item level.

  max-spread: <value>
    - The maximum relative offset for the modifier's value.

  Example:
    on-hit burn ability:
      cooldown: 6s, +/-10% average, max relative offset 10%
      duration: 6s, increased by 0.2s per item level

  Non-scaling modifier example:
    damage: 5 (no scaling specified)
    cooldown: scales as specified

  Note: To prevent scaling, set 'scale' to 0 or omit 'scale' and 'max-spread'.
```

Number based item statistics like armor/atk damage/... all scale according to the item level. However, so that items with the same level do not have the **exact same stat values**, a slight random offset is applied to each stat independently of the other stat offsets.

### Gemstone Handling and Drop Extra Gems Option

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Revision-ID-System/diff

Explains the handling of gemstones during item revision updates and the role of the `drop-extra-gems` option. This option ensures that gemstones that would otherwise be lost due to revision updates are returned to the player.

```APIDOC
Feature: Keep Gemstones

Configuration Option: `drop-extra-gems`

Description:
  This global option affects how gemstones are handled during item revision updates. When an item's revision ID is updated, existing gemstones are checked against the new template.

Functionality:
  - If gemstones would be deleted or become incompatible due to the revision update, and `drop-extra-gems` is set to `true`, these gemstones are returned to the player.
  - If the player's inventory is full, the gemstones will be dropped nearby.

Scope:
  This option is global and applies to all item revision operations within the system.

Purpose:
  To provide a fallback mechanism for players to recover gemstones that might be invalidated by item template updates, preventing loss of valuable item components.
```

### EnchantPlugin Interface

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Enchant-Plugins

The core interface for custom enchant plugins. It defines methods to identify custom enchants, handle their application to items, and retrieve namespaced keys. This interface supports enchantments managed via Bukkit's Enchantment interface, NBT data, or lore.

```java
/**
 * There are three types of enchant plugins.
 * - enchants saved using the Bukkit Enchantment interface (EcoEnchants, MythicEnchants)
 * - enchants saved in the NBT (AdvancedEnchants)
 * - enchants saved in lore only (CrazyEnchants)
 * <p>
 * Interface used to support plugins which use the Bukkit Enchantment
 * interface to register their enchantments. This makes enchant storage
 * so much easier for MMOItems.
 *
 * @param <T> The plugin class implementing Enchantment
 */
public interface EnchantPlugin<T extends Enchantment> {
    /**
     * @param enchant Enchant being checked
     * @return If this enchant plugin handles a given enchant
     */
    boolean isCustomEnchant(Enchantment enchant);
    /**
     * Called when an item is built. This should be used to add the enchantment
     * lines to the item lore or add any item tag required by the enchantment.
     *
     * @param builder Item being built
     * @param enchant Enchantment being applied
     * @param level   Enchant level
     */
    void handleEnchant(ItemStackBuilder builder, T enchant, int level);
    NamespacedKey getNamespacedKey(String key);
}
```

### MMOItems Recipe Properties

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Custom-Recipes/diff

Defines special properties that can be applied to custom recipes to modify crafting behavior, such as gem recovery and upgrade retention.

```APIDOC
Recipe Properties:

- `drop-gems: <true|false>`
  - Description: Determines if gems slotted into MMOItems used as ingredients are dropped and recoverable upon crafting.
  - Example: `drop-gems: true`

- `upgrades: <ADDITIVE|MAXIMUM|EVEN|MINIMUM|NONE>`
  - Description: Dictates how upgrade levels from ingredient MMOItems are handled in the crafted item.
    - `ADDITIVE`: Sums upgrade levels (e.g., +1 + +3 = +4).
    - `MAXIMUM`: Takes the highest upgrade level (e.g., +1 + +3 = +3).
    - `EVEN`: Averages upgrade levels (e.g., +1 + +3 = +2).
    - `MINIMUM`: Takes the lowest upgrade level (e.g., +1 + +3 = +1).
    - `NONE`: Discards all upgrade levels.
  - Example: `upgrades: ADDITIVE`
```

### CustomModelData for Custom Textures (1.14+)

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Custom-Item-Textures/diff

Explains the use of the CustomModelData NBTTag in Minecraft 1.14 and later versions for applying custom item textures. This method preserves item durability, unlike older durability-based systems. ```APIDOC
Minecraft NBTTag: CustomModelData

Description:
  Allows items to have custom textures without altering their durability. Introduced in Minecraft 1.14, it replaces older durability-based texture systems.

Usage:
  1. Set up a custom resource pack.
  2. In Minecraft, open the edition GUI for the item.
  3. Locate the 'Custom Model Data' option.
  4. Input a desired integer that corresponds to a texture defined in your resource pack.

Dependencies:
  - Minecraft version 1.14 or later.
  - A correctly configured resource pack.

Limitations:
  - Requires manual setup of resource packs and in-game configuration.
  - Relies on integer mapping between NBT data and resource pack assets.

### Enchantment Handling in Revision ID System

Source: https://gitlab.com/phoenix-dvpmt/mmoitems/-/wikis/Revision-ID-System/diff

Details the logic for keeping or updating item enchantments when their revision ID is updated based on template comparisons. It outlines how enchantments are updated if worse than the template, kept if better and obtainable, and how specific template stats like 'disable-enchanting' and 'disable-repairing' override these rules.

```APIDOC
Feature: Keep Enchantments

Description:
  Manages how existing enchantments on an item are treated when the item's revision ID is updated against a new template.

Rules:
  1. Update to Better Value: If an old enchantment is worse than the corresponding enchantment in the template, it updates to the template's better value.
  2. Keep Better Enchantment: If an old enchantment is better than the template's value, it is kept, provided it is still obtainable in vanilla Minecraft.
  3. Overrides:
     - If the template has `disable-enchanting` enabled, all enchantments are updated to match the template, regardless of their current value or the 'Keep Better Enchantment' rule.
     - If the template has `disable-repairing` enabled, similar to `disable-enchanting`, enchantments are updated to match the template.

Purpose:
  To ensure players do not lose their enchantments but can benefit from improved enchantments defined in item templates, while respecting specific template configurations that enforce standardization.
```

Feature: Breaking Soulbound Items

Description: Allows players to remove the soulbound property from an item.

- A specific consumable item.

Process:

Outcomes:
- Success: Soulbound property is removed.

Related:
